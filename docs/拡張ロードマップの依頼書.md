# 拡張ロードマップの依頼書

**この文書は、計画を立てる担当（プランナー役のLLM）へ渡すためのものです。**
読む人がリポジトリを見られない前提で、判断に要る事実をここに集めてあります。

数字は **2026-09-05 時点の `data/*.js` から実測**したものです（測り方は §9）。
古い数字が別の文書に残っていることがあります。**食い違ったらこちらを正としてください。**

---

## 1. 何を作ってほしいか

**今後の拡張のロードマップ**を1本。次の形で出してください。

### 出力の形

```
## 全体の方針（3〜5行）
   何を伸ばし、何を伸ばさないと決めたか。理由。

## 段（3〜5段）
   段ごとに:
   - 題目（何が遊べるようになるか。機能名ではなく、遊ぶ人から見た変化で書く）
   - 含まれる項目（1段あたり3〜7個）
   - この段を終えた時点で何が確かめられるか（受け入れの条件）
   - 前の段に依存する理由（無ければ「独立」と書く）

## 項目ごとの札
   - 題目
   - なぜやるか（**このゲームの現状のどの数字・どの問題に効くか**）
   - 分量の見積り（§4 の区分で「データだけ / 効果1つ / 仕組み / 画面」）
   - 測り方（何をもって成功とするか。§9 の道具で測れる形にすること）
   - 落とし穴（既知のものは §6 §7 から引く）

## やらないと決めたもの
   検討したが外したもの。**理由付きで。** これが一番あとで効きます。
```

### 粒度

**1項目 = 半日〜2日で終わる大きさ**にしてください。それより大きいものは分割を。
段は「ここで一度公開できる」区切りで切ってください（公開は §8）。

### 書かないでほしいこと

- **一般論としてのゲーム設計論。** 「プレイヤーの離脱を防ぐには」のような、
  このゲームの数字に紐づかない話は要りません
- **数字の裏付けが無い断定。** 分からないことは「未確認」と書いてください。
  この作業ログ群では、推測を事実として書いたことが何度も事故になっています
- **既に決着した論点の蒸し返し**（§7）。再開したいなら、決着の理由を否定する材料を添えて

## 2. このゲームは何か

**『灰銀の継承者』** — ブラウザで動く日本語のハック＆スラッシュRPG。
PWA として GitHub Pages で配信し、スマートフォンでも遊べます。

- **周回モード**が本体。フィールドを繰り返し回り、装備を拾い、レベルとスキルツリーを伸ばす
- **物語モード**は別プロファイルの短い読み物（現在4章）
- 戦闘は自動進行の**オート**が主。手動戦闘もあるが、周回の本体はオート
- 塔（階層を登る）と闘技場（ボス7体・通常/ハード）が腕試し枠

世界観は、旧文明がエーテルの充満によって崩壊し、すべてが灰になった後の世界。
「灰」は比喩であって、本当に灰が増えているわけではありません。

### 遊びの芯（設計書より）

**取捨選択がビルドになる。** スキルツリーは全342ノード・取り切りに3,076SPを要し、
上限のLv255・5凸でも **259SP しか得られません（取得率 8.4%）**。
全部は取れないので、何を捨てるかが個性になります。これは意図した形で、
「薄い」ではありません。

**系統タグは散らすほど強い。** [物理][魔術][遺物] の3系統は互いに乗算されるので、
1つに集中するより分散させたほうが伸びます（合計+60%を集中すると1.600倍、
3系統に分散すると1.728倍）。ビルド構築の核です。

## 4. 分量の見積りは「構造」で決まる

**このプロジェクトで最も効く制約です。** 同じ「1機能」でも、どこに触るかで手間が10倍違います。
ロードマップの見積りは、必ずこの区分で書いてください。

### ① データだけ（安い）

`data/*.js` への追記だけで増えるもの。**`src/` を触りません。**

キャラ・敵・技・装備・フィールド・依頼・宝箱・ツリーのノード・クラスのノード・物語のシーン。
**手順書が `docs/拡張コンテンツの作り方.md` にあり、外部の担当へそのまま委譲できます。**

> データを増やすのに `src/` を触る必要が出たら、それは設計が壊れかけている合図です。

### ② 効果を1つ足す（中くらい・落とし穴あり）

新しい種類の効果（例「回避したら次の攻撃が強くなる」）を足す場合、
**5ファイル7〜8箇所**を漏れなく書く必要があります。

| ファイル | 何を書くか |
|---|---|
| `data/effectkinds.js` | 登録簿 |
| `src/core/tree.js` | ①既定値 ②`switch` の `case` ③既知の一覧 |
| `data/nodecategories.js` | どの枝に並ぶか |
| `docs/拡張コンテンツの作り方.md` | 外部向けの表 |
| `test/tests.js` | ①検査一覧 ②ユニーク効果の検査 |

**1箇所でも漏らすと、書いたのに何も起きません。エラーも警告も出ません。**
さらに効果の届き先が3経路（`passives` / `situational` / 素の値）あり、
**取り違えても静かに無効になります。**

検証テストがこの全部を突き合わせているので、漏らせば必ず落ちます。
実際に「既定値と読み出しは書いたが登録簿に無い」という漏れを踏んでいます。

### ③ 仕組みを足す（高い）

戦闘の規則そのものを変えるもの。コンボを資源にした改修や、
フィールドを別モードから借りる仕組みなどがここ。
**必ず実測とセットで**（§9）。

### ④ 画面（高い・回帰しやすい）

`src/ui/`。テストが見ていない領域で、**過去の事故はここに集中しています**
（画面が開けない・背景が特定端末で見えない・入口が5世代前のキャッシュで塞がっていた）。

### ⑤ 絵（外部費用が発生する）

NovelAI で生成します。**課金されるので、指示があるまで走らせません。**
生成は逐次＋待ち時間を守ります（提供元への負荷）。
立ち絵の作り直しは1人あたり候補6〜10枚が目安。

## 5. 触ってはいけない前提

- **ESモジュールは使えません。** 素の `<script>` とグローバル `RPG` 名前空間。
  `file://` で開けることを要件にしているため。`import` / `export` を書くと動きません
- **データ駆動を崩さないこと**（§4①）
- **セーブの互換性。** 新しい項目は移行処理だけでなく**新規作成の初期形にも**置く。
  片方だけだと、書き出し→読み込みの往復が一致しなくなります（実際に起きました）
- **物語モードは別プロファイル。** 周回側へ値を漏らさないこと
- 公開ブランチは `main`。push するとそのまま配信されます

## 6. 同じ失敗を繰り返さないための記録

**これらは実際に起きたことです。** 計画に織り込んでください。

| 起きたこと | 教訓 |
|---|---|
| 状態異常の上限を素の値より低く置き、投資しても何も起きなかった | **上限は投資が届く位置に置く。** 上限は安全弁であって設計値ではない |
| 割合ダメージの状態異常を、通常アタッカーがつまみ食いするだけになった | **新しい軸を足すときは「専業が報われるか」ではなく「つまみ食いの投資効率」を先に測る** |
| 測定道具が実際のビルドより48%少ないSPしか使っておらず、結論が全部ずれていた | **道具を先に直す。** 測った数字より、測り方のほうが疑わしい |
| 装備していない状態で2回測って「勝てない」と判断した | **測定の前提条件を毎回確認する** |
| 「入口が無い」の原因が実装ではなく5世代前のキャッシュだった | **症状と原因は別の場所にある** |
| 設定文書の付録が実装とずれていた | **数値を文章に書いたら、テストで実装と突き合わせる**（いまは自動で検査） |
| 顔の自動計測が武器や装飾を頭と誤認し、11人中9人で外れた。**数値が中央に見えても外れていた** | **道具の出力を目で確かめる工程を省かない** |
| プロンプトのパーサが特定の書き方で黙って別の値に差し替わっていた | **「出力は出るが中身が違う」型の失敗がいちばん見つからない。落ちたら言わせる** |

## 7. 既に決着した論点（蒸し返さない）

理由まで含めて `docs/保留中のアイデア.md` にあります。要約:

- **クラス点が全部取れないのは意図どおり。** Lv255で51点、1分岐フルに85〜88点。
  6クラス間の差は3点以内なので偏りではない
- **終焉の一撃が44M出る件は直さない**と決めた
- **闘技場の通常モードは「解けば倒せる」で成立している**（誤判定だった）
- **反射・棘は遅れていたのではなく「取ると損」だった**（対処済み）
- **SPは余っていない**（取得率8.4%）。ただし専任の支援役・回復役がSPを持て余す件は
  **別の話として残っています**（軸そのものが浅い）
- **敵の染色**（属性を塗り替える）は、**数値の詰めに一番時間がかかる**ことを理由に見送り中。
  敵の属性は被ダメージ側の相性も決めているので、染めると有利不利が二重に動く。
  実装そのものは軽い（`statusEffects` に積んで `elementMultiplier` の参照先を差し替えるだけ）
- **雑魚敵の見た目の個体差**は、**初回読み込みが太る**ことと
  **素材の質がばらつくと逆効果**であることを理由に見送り中

## 8. いま開いている設計問題

### ★ 終盤にオート用の張り合いが無い（未着手・最重要）

全12フィールドを測り直したところ、**終盤はどれも勝率100%・残HP95〜100%・4人生存**。
最上位の「終わりなき回廊」（敵は常にパーティ+15）でも無傷で終わります。

**難度を上げる方向は行き止まり**だと分かっています。

- オートで勝てない難度にする → 周回する人は、オートで100%回せる手前のフィールドへ移るだけ。
  そこが「手で何度も回る物好きのための場所」になる
- 報酬を盛って引き止める → よほど盛らないと釣り合わず、盛れば手前のフィールドが死ぬ

**周回の本体はオートなので、オートで回せることが参加の条件**になっています。

それでも**ヌルいとオート用にパーティを組む楽しみが減る**、という問題は残ります。

未着手の方向（どれも検証していません）:

- **勝敗ではなく速度で競わせる。** 1周のラウンド数や時間を指標にする
- **オートの外に難度を置く。** 闘技場のような手動前提の場所を別に持つ
- **編成に条件を付ける。** 依頼の縛りのように「この構成で回れるか」を問う

**ロードマップでは、この問題への立場を必ず示してください。**
解くのか、後回しにするのか、別の形に言い換えるのか。

### 支援・属性・状態異常の軸に「代償つきの終端」が無い

上級帯の一角には【極】ノード（強いが代償を伴う）を入れましたが、
上の3軸には無く、**素直に積み上がるだけ**になっています。同じ作法で足せますが、
1つずつ実測が要ります。

### 小さめの手持ち

オート残り0の表示不具合（再現待ち）、コンボの型×属性×系統タグの量産、
`eq_rod` のユニークが無い、遺物の大技の枠。

## 9. 判断は実測でしてください

**感覚で決めないこと。** 次の道具があります。

| 道具 | 測れるもの |
|---|---|
| `test/index.html` | 検証テスト（現在 1,358 件）。データ整合・計算規則 |
| `test/balance.html` | 勝率・ラウンド数・SP収支・フィールドの経済 |
| `test/builds.html` | 属性戦略が並立しているか |
| `tools/count_content.py` | 実装の実数。設定文書の付録との突き合わせも自動 |

測るときの作法:

- **上乗せではなく置き換えで測る。** 支援パッシブを攻撃ビルドに足すと、
  枠の対価を払っていないので過大評価になります。パーティの1枠を実際に差し替える
- **基準は Lv255（`maxLevelCap`）。** Lv150で測ると上限を伸ばした先で破綻します
- **勝率よりラウンド数のほうが安定します。** 20戦程度では勝率は数ポイント揺れる
- **1回に1つだけ変える**

ロードマップの各項目には、**この道具で測れる受け入れ条件**を書いてください。
「面白くなる」ではなく「オートのラウンド数が○○帯に収まる」の形で。

## 10. 運用の前提

- **開発は1人＋LLM。** データ追加のような定型作業は外部の担当へ委譲できますが、
  **採否の判断は人が持ちます**（立ち絵45人の作り直しはこの分担で回りました）
- **長い作業は `work/<題目>` ブランチで進め、通しで動いてから `main` へ**。
  途中を push すると作りかけがそのまま配られます
- **文脈は途中で圧縮されます。** 進行中の状態は `docs/作業ログ/<題目>.md` に1本残し、
  検証が通った単位ごとにコミットする運用です。
  **ロードマップの段は、この「再開できる単位」と一致させてください**
- 絵の生成は課金され、指示があるまで走らせません
