## 全体の方針

終盤の安定したオート周回を土台に、編成を工夫する目的と、その成果を確かめる場所を増やす。
測定方法を整え、既存の依頼で小さく試し、装備の選択肢、専門ビルド、中間帯と物語の順に広げる。
総数の均等化を目標にせず、既存の選択肢ではできない遊びを増やす。
SP上限や通常周回の難度を一律に引き上げず、259SPで何を捨てるかという設計を維持する。
継続的に遊ばれるかは戦闘シミュレーションだけでは判定できない。数値検証とプレイ後の採否判断を分ける。

## 実装・公開の区切り

- 実装開始時に `work/auto-build-expansion` などの作業ブランチを使う。計画作成だけの段階では公開しない。
- 作業状態は `docs/作業ログ/オート編成拡張.md` に集約。現在の項目、前提、結果、未確認、次の作業を記録する。測定の生データは `_scratch/` に置く。
- 各項目の検証が通った単位でコミットする。段ごとに通しの検証・試遊・採否判断を行い、採用分を公開できる状態へまとめる。
- 公開前は `test/index.html`、`test/balance.html`、`test/builds.html` と実画面を確認し、`publish_check.py` を実行する。
- 作業ブランチではキャッシュ版上げ・公開先ポーリングを行わない。公開時に事前キャッシュを確認・更新し、版上げ、mainへの反映、push、公開先の版と動作確認、正常版の印付けを順に行う。詳細は `hakusura-release` スキルに従う。
- 画像生成、新しいセーブ項目、大きな画面改修は現計画に含めない。必要になった場合は影響と分量を具体化して計画を更新する。

## 今回見送るものと再開条件

| 対象 | 見送る理由 | 再開条件 |
|---|---|---|
| 通常フィールドの一律強化 | 安定周回できる手前へ戻る問題を解決しない | 別の目的と報酬設計を実測で示せる |
| 技9マスの一括補完 | 空欄数だけでは需要が分からない | 採用した編成で必要な技が不足する |
| 新フィールド・仲間の大量追加 | 既存12フィールド・60人を組み替える目的を先に作る | 既存では成立しない攻略や物語が決まる |
| 単独使用33効果の量産 | 要のノードまで均す必要はない | 特定ビルドの投資先不足を測定できる |
| 塔の全フィールド網羅 | 参照数の不足と遊びの不足は別 | 既存の階層帯にない攻略が決まる |
| 自己ベスト画面・ランキング | 指標と試作の成立が先 | A4で繰り返し試したい目的が確認できる |
| 速度比例の追加報酬 | 速い編成は既に時間当たり収益で有利 | 経済比較で過度な集中を避けられる |
| 敵の染色・画像差分 | 既存の保留理由が未解消 | 元の保留文書の再開条件を満たす |
| SP・クラス点上限の増加 | 全取得できない設計は意図どおり | 現計画の対象外 |

オート残り0の表示不具合は、再現手順が得られた時点で独立の修正として扱う。未再現のまま工数や原因を確定しない。
