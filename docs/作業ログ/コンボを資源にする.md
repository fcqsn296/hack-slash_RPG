# 弱点コンボを「消費できる資源」にする

## 何が壊れていたか

コンボは**貯まるだけで、使い道が火力しかなかった**。そのため3つが同時に起きていた。

| | |
|---|---|
| ① つまみ食い | 段は `battle.combo` の1本でパーティ共有。**振っていない人にも無料で乗る**（5段×8%＝+40%） |
| ② 遅い | 積むのに手数が要り、2〜3ラウンドで終わる戦闘では一度も仕事をしない |
| ③ 効率が悪い | 全部振って49SPで+120%。三系統掌握は9SPで×1.64 |

**火力の上限を伸ばしても①は直らない。** つまみ食いの取り分も一緒に増えるため。

## どう直したか

段を**消費する資源**にした。読み書きの口は `src/` に1箇所だけで、
技側の `params.combo` を `resolveCombo` が読む。

```
needs    これ未満なら不発（前提型）
spend    発動時に消費する段（消費型）
spendAll 持っている段を全部使う。消費量が per に掛かる
per      段1つあたりの上乗せ
gain     撃ったあとに積む段（積み型）
```

**型ごとに効果キーを作らない。** 作ると5ファイル7箇所の登録が型の数だけ要り、
しかも漏らすと静かに無効になる。宣言を1箇所で読む形なら、
新しい型はデータを書くだけで足せる。

## 実測（闘技場の主ハード・259SPを使い切り・耐久を切り離す・9回の中央値）

| 構成 | 決着 |
|---|---:|
| コンボ軸 継ぎ穂だけ | **11R** |
| コンボ軸 手繰り→出涸らし | 12R |
| コンボ軸 断ち切る一閃だけ | 12R |
| 素直な火力（同じ259SP） | **14R** |

**③は解消した。** 同じSPでコンボ軸のほうが速い。

| | 決着 | 最高段 |
|---|---:|---:|
| 専業（コンボへ155SP） | 12R | **5段** |
| つまみ食い（コンボへ0SP） | 12R | **2段** |

**①も塞がった。** 消費型は撃てるが払う段が無く、火力は素の技と変わらない。

## 【判断】上限アップ（重ねの理）は死んでいるが、残す

段は5で回っていて、**上限8には一度も届かない**。18SP 払って使われない投資である。

外す案もあったが、**残すことにした。**

- 段数そのものを参照する技やパッシブを作れば、そこで軸になる。
  **上限が高いこと自体に価値を付ける余地**を先に潰したくない
- 手を入れる前のコンボ軸は**ほぼ空気**だった。上限アップが当面死んでいても、
  全体としては前より良い状態にある
- 使い道を作る前に「積む速さ」だけ上げると、消費型が強くなりすぎる恐れがある

**次に触るときの手掛かり:** 段数（または上限に対する充填率）を読む型を足す。
`params.combo` に読み方を1つ増やすだけで済むはず。

## 途中で踏んだ穴

**`comboThreshold` を既定値だけ置いて登録していなかった。**
`resolveCombo` で読み、`tree.js` の既定値にも置いたのに、登録簿・`switch`・
既知一覧・手引き・検査への登録を全部飛ばしていた。**常に0を読み続ける、
静かに死んだ状態**である。`CLAUDE.md` §2 の罠をそのまま踏んだ。

**`battle.combo.best` が開幕ぶんを数えていなかった。**
`先んじる連鎖` で開幕から段を持っていても、一度も更新されずに終わると
「最高0段」と記録される。測定で「継ぎ穂＝最高0段」と出て、
危うく「積めていない」と誤読するところだった。

**検査が登録漏れを4件とも名指しで止めた。** うち1件は設計違反で、
攻撃技にクールダウンを付けていた（大技は上限に潰されているので
待ち時間まで課さない、という決まりがある）。段を要求すること自体が
既に対価なので、二重に縛らず外した。

## いま入っているもの

- ノード9つ（元は4つ）。積む5・読む/使う4
- 技5本。型ごとに1本の見本を兼ねる
- 持ち主: 主人公（手繰り）/ アストラ（継ぎ穂）/ ルーメン（断ち切る一閃）/
  エンバー（出涸らし）/ ノクス（削ぎ落とし）

**型 × 属性 × 系統タグ での量産はデータを書くだけ**なので、以降は任せられる。
