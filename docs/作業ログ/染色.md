# 染色（敵の属性を塗り替える）

保留中のアイデアから着手。2026-08-20 に保留、2026-09-18 に実装。

## なぜ空いていたのか

攻撃側の属性操作は**ツリーが埋め尽くしている**。

| 既存のツリー効果 | 何をするか |
|---|---|
| `element_convert` | 自分の全攻撃を1属性に固定する |
| `dual_element` | 2属性で判定して良い方を取る |
| `element_adapt` | 不利を等倍まで引き上げる |
| `element_mastery` | 特定属性の有利倍率を伸ばす |
| `element_pierce` | 不利属性の目減りを減らす |

一方で、**受け側の属性に触る手段は1つも無かった**。ここが構造的に空いている。
属性特化ビルドは「刺さらないフィールド」で腐るという弱点を抱えているが、
染色があればその弱点を連れて行く仲間で補える。

## 保留の理由を、どう解いたか

保留時に挙げていた3つの懸念と、その始末。

### ① 全体化すると属性特化がそのまま万能になる

単体・短ターン（2ターン）にした。「どの1体をいつ染めるか」が残る。
実測でも**ボスに使うと得、雑魚に使うと損**という形に収まっている。

### ② 敵の属性は被ダメージ側の相性も決めている

**塗るのは「受ける側の属性」だけにした。** `toDefender` が返す属性だけを
差し替え、敵の攻撃は塗る前の属性のまま飛んでくる。
闘技場の `elementNull` が相性を一方向にだけ均しているのと同じ立ち位置。

両方向にすると有利不利が二重に動き、1手の価値が場面によって跳ね上がる。
実測: 与ダメ 1.50倍 / 被ダメ 1.00倍。

### ③ バランス検証を属性別に見直す必要がある

見直す必要が無かった。周回シミュレーションはオートで回るが、
**autoplay は染色を読まない**（コンボと同じ扱い）。
手動で遊ぶ軸なので、周回の数字は動かない。実際に全項目 ✔ のまま。

## 踏んだ罠

**既定の染め色を「撃った本人の属性」にしていた。** 火のパーティが相手を火に
染める形になり、有利どころか何も起きない。実測でボス戦が
14.25R → 15.20R と、**染めたほうが遅くなっていた**。

正しくは「自分の属性が食う色」。火なら風へ。`STRONG_AGAINST` を引けば
一意に決まるので、技ごとに書かせる必要もない。直したら 10.85R になった。

もう一つ。手順書の検査は「plugin に書けるもの」から「バフは3つ」までを
1つの表として読む。その範囲に別の表を割り込ませると、
**その行が plugin 名として拾われて落ちる**。節は範囲の外へ置くこと。

## 実測（Lv200・火に固定した4人・20戦）

| 条件 | 染めない | ボスを染める |
|---|---|---|
| 闇のボス単体（火は不利） | 14.25R | **10.85R**（−24%） |
| 闇の5戦通し | 38.35R | **34.70R**（−10%） |

持続を伸ばしても大差ない（2T 10.85R / 3T 10.55R / 4T 10.30R）ので、
いちばん短い2ターンで据え置いた。保留時の方針どおり。
