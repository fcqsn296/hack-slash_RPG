# 測定エージェントの手順

難度や投資先の価値を**手動相当の操作で**測るための手順書。
サブエージェントに渡す前提で書いてある。

**この文書の値は実測から来ている。** 推測で書き換えないこと。

---

## 0. なぜ「手動相当」なのか

**オートは弱点コンボを見ない。** これは意図的な設計で、
手動で段取りを組んだ人だけが受け取る報酬として作られている（`src/core/battle.js` §10.6）。
手番の前借り（`borrowTurn`）も、段の出口（継ぎ手）も、オートは使わない。

つまり**オートで測れるのは「オートで届く範囲の難度」までで、それが上限ではなく下限**。

```
オートで100%勝てる → 手動なら確実に勝てる（＝関門として成立していない）
オートで0%         → 手動で勝てるかは分からない（結論を出せない）
```

`noAuto` の依頼（アルカナの解放2件など）を測るときは、**必ず手で行動を選ぶ**。

## 1. 土台のセーブ

```
_scratch/save_testbed_lv255.json
```

- 66人すべて **Lv255 / peak 255**
- ツリーは全員 `docs/強いビルドの組み方.md` §7.0 の処方（248SP）
- クラスは6種を順に配ってある
- 装備は在庫から自動装備で重複なく（66人×6枠＝396個／在庫 2,205個）
- 限界突破は元のまま（盛ると「0凸の実データ」と比べられなくなる）

**`peak` が 255 なのが要点。** `RPG.state.setLevel` は `peak` まで無料で
行き来できる（§6.7）ので、**1つのセーブで全レベル帯を試せる**。
Lv150 の関門を測りたければ下げればよい。

| | ATK | DEF | HP |
|---|---|---|---|
| Lv255 | 23,556 | 14,227 | 25,900 |
| Lv150 へ下げた | 15,240 | 9,411 | 16,786 |
| （参考）実プレイのセーブ Lv255 | 27,434 | 14,061 | 9,377 |

作り直すときは:

```bash
python tools/make_testbed_save.py _scratch/<元セーブ>.json _scratch/save_testbed_lv255.json
```

処方を変えたら `tools/testbed_assign.txt` と `TREE` も作り直す必要がある（手順は §7）。

### ⚠ この土台は終盤の難度には使えない（2026-09-17 に判明）

**`autoequip.optimize` はセットを組まない。** 素のステータスで選ぶので、
**装備セットの効果が丸ごと抜ける**。実測で並べるとこうなる。

| | セット効果 | 軽減 | 多段 |
|---|---|---|---|
| 実プレイのセーブ（主人公） | `set_undying` 発動（上限突破+0.9・大技+0.6） | 60.7% | — |
| 土台（自動装備） | **発動なし**（`setEffects: {}`） | 44.2% | 1 |

結果として、**土台は ATK が高いのに勝てない**という逆転が起きる。

| | 土台 | 実セーブ |
|---|---|---|
| `q_endless_vigil`（8R・敵HP×35） | **0%** | **100% / 5.9R** |
| `q_three_at_the_verge`（3人・敵能力×14） | **0%** | **100% / 5.3R** |

エンバーは土台で ATK 25,699・実セーブで 6,530。それでも実セーブが勝つ。
**ダメージ上限は1発ごとにかかる**ので、発数（多段3 対 1）が実質の天井を決める。
土台に多段3を足すと `q_endless_vigil` は 0% → 75% になった（原因の裏取り済み）。

`q_three_at_the_verge` のほうは生存側で、軽減 44.2% では1ラウンド目に
3.4〜4.6万ダメージで落ちる。

**在庫のセット駒は158個しかなく、装飾に偏っている**（`set_undying` は武器6個）。
66人全員に4駒セットを組むことはできない。

#### だからどう使うか

| 問い | 使うもの |
|---|---|
| 終盤の関門は成立しているか | **実プレイのセーブ**（`_scratch/save_latest_*.json`） |
| 到達直後の帯で手も出ないか | `makeParty`（その帯の宝箱） |
| レベル帯を振って傾向を見る | 土台（ただし**絶対値は信じない**） |

**土台で0%が出ても「達成不能」と結論してはいけない。** 実セーブで測り直すこと。
この取り違えで、正常に動いている依頼2件を「達成不能」と報告しかけた。

### この土台が模しているもの・していないもの

**装備は実プレイの在庫（LEGEND 2,193個）から配っている。** つまり
「よく集めた人」であって「そのレベル帯に到達したばかりの人」ではない。

同じ Lv150 で比べると差が出る。

| | 4人・HP×12・fl_endless |
|---|---|
| 土台のセーブ（実在庫） | 勝った（2R） |
| `makeParty`（その帯の宝箱） | 0% |

**難度を決めるときは、どちらの模型で測っているかを必ず書くこと。**
到達直後の関門を見たいなら `makeParty`、育った人の手応えを見たいなら土台。

### 新しい技を測るときは処方に足す

`REFERENCE.plan` は `docs/強いビルドの組み方.md` §7.0 をそのまま写したもので、
**それより後に足した技のノードは入っていない**（例: `tr_grant_reprise` = 継ぎ手）。
入っていないと、手動の方針が技を見つけられず**黙って何もしない**。

**ただし足すだけでは入らない。** `investPlan` は plan の順に**上限まで**振るので、
処方だけで SP を使い切る帯では、後から足したノードに回る SP が残らない。
実測（`tr_grant_reprise` は上級・5SP）:

| | Lv200（199SP） | Lv255（254SP） |
|---|---|---|
| 末尾に足す | 取れない | — |
| 先頭に差し込む | **取れない**（199/199 使い切り） | 取れる（253/254） |

先頭に置いても Lv200 では入らない。上級ノードはティアが開くまで `canInvest` が
false を返し、開いた頃には SP が尽きているため。**Lv255 で測るか、
処方から何か落として枠を作ること。**

```js
// Lv255 なら入る
const plan = ['tr_grant_reprise'].concat(RPG.buildLab.REFERENCE.plan);
```

**方針が技を撃てたかどうかを毎回数えること。** 0 なら測定が成立していない。
実際これで「継ぎ手を使った回数 0」のまま2回測り、
2回目でようやく SP 不足だと分かった。

## 2. セーブを壊さないための決まり

**ここを破ると取り返しが付かない。** 実際に localhost のセーブを1つ失っている
（9,426,393G・66体・装備2,205個／2026-09-11）。

- **`localStorage` を触る前に、控えをファイルへ書き出す。**
  ページ内の変数（`window.__bk` など）に置くと、リロードで変数ごと消える
- **テストページを実行中にリロードしない。** `test/tests.js` は各ブロックで
  `localStorage` を控えて書き戻すが、途中でリロードすると書き戻しが走らない
- 測るだけなら **`localStorage` を触る必要は無い**。
  下の測り方は全部「セーブを読み込まずに、JSON からユニットを組む」形にしてある

```js
// これでよい。localStorage には触らない
const d = await (await fetch('../_scratch/save_testbed_lv255.json')).json();
const g = d.game || d;
const u = RPG.units.buildCharacterUnit(g.characters.ch_hero, g.inventory);
```

## 3. 測り方の骨格

`test/builds.html` を開いて、そのページの文脈で走らせる
（`units` / `battle` / `autoplay` / `autoequip` / `buildLab` が揃っている）。
`data/quests.js` は読まれていないので、依頼を見るなら差し込む。

```js
const s = document.createElement('script');
s.src = '../data/quests.js';
document.head.appendChild(s);
```

### 手動で戦う枠

```js
function fight(party, cfg, policy) {
  party.forEach((u, k) => { u.side = 'party'; u.key = 'p' + k; });
  // **party を cfg に入れること。** 別の引数で渡したまま start を呼ぶと
  // battle.js の中で party.forEach が落ちる（この手順書を書いた直後に踏んだ）。
  RPG.rng.seed(cfg.seed);                 // 種を止める。止めないと比較にならない
  const b = RPG.battle.start(Object.assign({}, cfg, { party }));
  let guard = 0;
  while (!b.finished && guard++ < 9000) {
    if (b.phase === 'wave_clear') { RPG.battle.advanceWave(b); continue; }
    const act = policy(b);                // ← ここが「手動」の中身
    if (!act) break;
    RPG.battle.commandSkill(b, act.skillId, act.targets, act.opts || {});
  }
  RPG.rng.seed(null);
  return { victory: !!b.victory, rounds: b.round, log: b.log.map(l => l.text) };
}
```

`policy` に `RPG.autoplay.chooseAction` を渡せばオート、
自分で書けば手動相当になる。**`guard` は必ず置く**（決着しない編成がある）。

**素朴な方針はオートより弱い。** 「段が2以上なら継ぎ手」という見本を書いたら、
継ぎ手を37回撃つかわりに殴らなくなり、オートの10ラウンド敗北に対して
25ラウンド敗北になった。手動が強いのは**段取りを組んだとき**だけで、
条件を1つ書いただけでは弱くなる。

方針を書いたら、まず**オートと並べて測る**こと。
オートに負けているなら方針が悪い（機能や難度の話ではない）。

### 手動の方針を書くときに見る値

```js
b.combo.count                      // 段（パーティ共有）
b.party[i].cooldowns               // { 技ID: 次に使えるラウンド }
RPG.battle.skillReady(b, u, sid)   // 撃てるか。{ ok, reason, waitRounds }
b.party[i].turnDebt                // 吊るされた男の負債（§21）
b.party[i].extraActions            // そのラウンドに得た再行動（上限3）
b.arena && b.arena.gimmicks        // 闘技場の仕掛け
```

段を使う技は `RPG.data.skills[sid].params.combo` を持つ。
**段を積むのはアタッカー、使うのは支援**という関係があるので、
手動の方針は「誰が積み、誰が使うか」を明示して書くこと。

## 4. 踏んだ罠（全部実際に踏んだ）

### `damage.calc` を直接呼ぶと 3.8倍ずれる

`battle.js` がその外側で重ねるものが全部抜ける。実測で確かめた漏れ:

```
highPowerBoost 2.15   大技だけ +215%
firstRoundPower 0.4   1ラウンド目 +40%
escalate 2            累撃（撃つたびに倍）
overkillCarry 0.6     持ち越し
adapt 2               全属性有利
```

**1発の威力を測るときも `battle.start` → `commandSkill` を通し、
ログの数字を読む。** 実機のスクリーンショットと突き合わせて確認済み。

### 縛りを効かせたいなら `rules` ではなく `quest` を渡す

`battle.js:1134` はこう書いてある。

```js
const rules = (quest && quest.rules) || {};
```

**`config.rules` は読まれていない。** 依頼の縛り（`maxRounds` / `allAlive` /
`maxParty` など）を効かせたいなら、**依頼オブジェクトそのものを渡す**。

```js
RPG.battle.start({ fieldId, waves, bossFinale, party, quest: RPG.data.quests[qid] });
```

`rules` を渡して「効かない」と結論し、ラウンドを手で数える回り道をした。
手で数えるのは、縛りの有無を自分で切り替えて比べたいときだけでよい。

### ラウンド数は `totalRounds` で見る。`round` はウェーブごとに戻る

`battle.round` は**ウェーブが変わると1へリセットされる**（`battle.js:1337`）。
`maxRounds` の判定は `battle.totalRounds`（通算）を見ている。

実測（fl_endless・5ウェーブ・4人・Lv255）:

| | `b.round` の平均 | `totalRounds` の平均 |
|---|---|---|
| 敵HP×12 | 1.0 | **6.0** |
| 敵HP×35 | 3.4 | **11.4** |

**`round` で測ると6分の1に見える。** 「戦闘は1ラウンドで終わる」と
繰り返し書いてしまったが、それは1ウェーブぶんの数だった。

ただし**クールダウンは `battle.round` を見ている**（ウェーブごとに戻る）。
「CD4の技は1ラウンドで終わるウェーブでは永久に撃てない」はそのまま成立する。
**どちらのラウンドの話をしているのかを、毎回はっきりさせること。**

### 勝率は終盤で天井に張り付く

推奨レベルでは15ビルド中12個が勝率の振れ幅ぴったり 0.00 だった。
**差を見るなら手数（コマンド数）かラウンド数。** 勝率は
「どのビルドでも周回できる」の確認に使う。

### 総ダメージは指標にならない

弱くすると手数が増えるので、**総ダメージは逆に増える**。
実際それで「上限突破を外したら総ダメージが34%増えた」という逆の結果が出た。

### 比較用の雛形ビルドは実プレイの15%しかない

`RPG.buildLab.BUILDS` の15種は Lv255 で ATK 4,074（実データ 27,434）。
**難度を決めるときは `RPG.buildLab.REFERENCE` を使う**（同 22,697・83%）。
雛形で決めて、Lv255でも勝率10%の関門を作りかけた。

### 上限減衰を忘れると結論が逆になる

終盤の素ダメージは上限の 2.5〜9倍。超過分は10%しか残らないので、
**威力%はほぼ効かない**（+60% が実効 +13%）。
「威力が上がったのに数字が動かない」ときは、まず上限を疑う。

```js
const cap = 500000 * (1 + unit.capBreak);   // これを超えた分は 1/10
```

### 1ラウンドで終わる戦闘では「ラウンドを跨ぐもの」が測れない

推奨レベルの戦闘は実測 1.0〜3.5 ラウンド。クールダウン・毎ラウンドの減衰・
解禁ラウンドは**周回では一度も発火しない**。
長さが要るなら `enemyScale: { hp: N }` で伸ばす。**HPだけにすること**
（全能力×10 は敵の一撃が味方の最大HPの478%になり、一撃死の二択になる）。

ただし HP を盛っても限界がある。実データのビルドは **HP×160 でも1ラウンド**で
終わった。負けは消耗ではなく一撃死だった。

## 5. 守ること（`CLAUDE.md` §3）

- **1回に1つだけ変える。** 2つ動かすとどちらが効いたか分からない
- **上乗せではなく置き換えで測る。** 支援を足すのではなく、1枠を差し替える
- **基準は `maxLevelCap`（255）。** 150 で測ると伸ばした先で破綻する
- 同じ種で同じ結果が出ることを毎回確かめる（出なければ比較が成り立っていない）
- 試行は最低10回。勝率は20戦でも数ポイント揺れる

## 6. 報告の形

**数字と、その数字が出た条件を必ず一緒に出す。**

```
条件: fl_endless / waves 5 / bossFinale / enemyScale {hp:12} / 4人 / Lv200 / 種 20260917+ / 10回
結果: 勝率 80% / 平均 4.5R / 3R以内 20% / 5R以内 60%
```

- **測れなかったことは「測れなかった」と書く。** 0% は「難しい」ではなく
  「この条件では結論が出ない」ことがある
- 自分の測り方を疑う。**同じ条件で2つの極端な値が出たら、まず harness を疑う**
  （単騎0%と4人100%の間に中間が無い、など）
- 新しく分かったことは、書いた場所に `@知見` の印を付ける
  （`python tools/build_knowledge_index.py` で索引が更新される）

## 7. 土台を作り直す手順

処方（`test/builds.js` の `REFERENCE.plan`）を変えたら、割り当て表も作り直す。

1. `test/builds.html` を開く
2. 次を走らせて、出た表を `tools/testbed_assign.txt` へ貼る

```js
(async () => {
  const d = await (await fetch('../_scratch/<元セーブ>.json')).json();
  const g = d.game || d;
  const plan = RPG.buildLab.REFERENCE.plan;
  const classes = Object.keys(RPG.data.classes);
  const inv = g.inventory.slice(); const used = new Set();
  const rows = []; let n = 0; let tree = null;
  for (const id of Object.keys(g.characters)) {
    if (!RPG.data.characters[id]) continue;
    const cs = { id, level: 255, exp: 0, peak: 255,
      limitBreak: g.characters[id].limitBreak || 0, tree: {},
      klass: classes[n % classes.length], klassTree: {},
      equipped: { weapon: [], armor: [], accessory: [] } };
    RPG.buildLab.investPlan(cs, plan);
    tree = tree || cs.tree;
    const res = RPG.autoequip.optimize(cs, inv.filter(it => !used.has(it.uid)));
    cs.equipped = res.equipped;
    for (const s of Object.keys(cs.equipped)) for (const u of cs.equipped[s]) used.add(u);
    rows.push([id, cs.klass, cs.equipped.weapon.join('.'),
      cs.equipped.armor.join('.'), cs.equipped.accessory.join('.')].join('|'));
    n++;
  }
  return { tree, rows };            // tree は make_testbed_save.py の TREE へ
})()
```

3. `python tools/make_testbed_save.py <元セーブ> _scratch/save_testbed_lv255.json`
4. 出来たセーブでユニットが組めることを確かめる（装備の欠けが 0 人であること）

**`uid` の重複と在庫に無い装備は、スクリプトが止めて教える。**
黙って壊れた土台で測るのがいちばん危ないので、そこは通さないようにしてある。
